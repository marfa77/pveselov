# Ep 03 — Pick a few fights
slug: pick-a-few-fights

## Spoken

Hi, this is Pavel Veselov. Building AI in the Enterprise — a guide for IT directors who have to make this real.

You have looked. You know the spend, the shadow tools, the weak pilots. Now comes the temptation to please everyone with a long use-case list. Do not. Episode three is about picking a few fights you can win. In the playbook this is phase two: choose where to play.

Concentrate on a few domains where AI output can be checked cheaply and the organisation can absorb the result. That sentence saves years.

First move: pick three to five business domains, not a catalogue of use cases. Each domain needs a measurable P and L line and a walk of the end-to-end workflow with the people who do the work. Done when each domain has a C-suite owner and a baseline metric. Harvard Business Review's authors describe companies stuck in a micro-productivity trap that start from long use-case lists. The ones that escape narrow AI to a few strategic domains. BCG finds future-built companies much more likely to fund AI as one multiyear program than as a scatter of experiments.

Second: apply a verifiability test. Score candidate workflows on five traits — text-based, repetitive, natural human review, limited regulation, verifiable output. Start with the highest scores. Done when your first wave only contains workflows where a wrong answer is caught cheaply. Andreessen Horowitz's work on where enterprises actually adopt AI shows adoption following verifiability more than raw model cleverness. Coding leads because code runs or it does not. Support works because the worst case is a hand-off to a person.

Third: check that the organisation can absorb the result. How much of the value chain do you control. How many technologies must combine. Run a short pre-mortem on the usual failure for that position. Done when each initiative names who will put the output into production, not only who builds it. The HBR story about GM's generatively designed seat bracket is the warning: lighter, stronger, and never in production because the factories were built for stamped steel. A better AI answer is worth zero if the factory — or the process — cannot use it.

Fourth: decide buy, partner, or build for each workflow. Default to buying or partnering for commodity capabilities. Build where the workflow differentiates you, or where building in-house is honestly cheaper than the licence. Done when every significant SaaS renewal gets an explicit build-versus-buy check. MIT's GenAI Divide found external partnerships reaching deployment about twice as often as internal builds, in self-reported data. McKinsey found about a third of respondents had dropped at least one software purchase because agentic coding let them build it inside. Those two facts sit in tension. We will hold that properly in episode eight. For now: write the decision down per workflow.

How this feels in the room. You will disappoint people whose pet use case did not make the cut. That is the job. A short list with owners and baselines is kindness. A long list with no baseline is theatre.

This week.

Name three domains, not thirty use cases. One sentence each on why the P and L cares.

For each domain, write the baseline metric and the C-suite owner. If you cannot name both, it is not ready.

Score your top workflows on the five verifiability traits. Keep only the high scores for wave one.

For each keeper, write buy, partner, or build — and why.

Next: change the work, not the slide — how to rebuild a workflow with the people who live in it.
